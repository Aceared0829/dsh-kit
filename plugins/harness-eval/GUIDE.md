# harness-eval — 自改进系统说明

> 版本：S1–S4 完成，闭环可用
> 位置：本库的 `plugins/harness-eval`（安装后是 profile 里的 `link:` 依赖）
> 本文写给「几天后回来接着用」的自己

---

## 一、这东西到底是什么

**一句话**：它把「某个改动到底有没有让 agent 变好」变成一个可以自动回答的问题。

不是一个 GUI 工具，也不只服务于 GUI。它的四层能力与具体场景无关：

| 层 | 做什么 | 跟具体场景的关系 |
|---|---|---|
| S1 观测 | 从会话日志算出 token、错误码、重试、重复调用、harness 签名 | 无关，对任何工具都成立 |
| S2 对比 | 判断两次运行是不是「可控对比」 | 无关 |
| S3 行动 | 改文件 + 记账 + 边界检查 + 回滚 | 无关 |
| S4 判定 | 按规则给出 kept / reverted / inconclusive | 无关 |

**GUI 只是一个实验靶子**：因为它的重复调用最极端（同参数 20 次）、原因清楚、指标干净。换目标不用改机制。

### 一个包，两个面

`dsh-harness-eval` 这一个包，同时是「一个插件」和「一套命令行工具」。**不要为此新建插件或入口。**

| 部分 | 谁运行 | 改它要重启吗 |
|---|---|---|
| `lib/index.js`、`lib/client.js`（投影、工具、guard、界面） | Host / 浏览器自动 | **要** |
| `loop.mjs`、`export.mjs`、`verify.mjs`、`gate.mjs` | 你手动跑 | **不要**（每次新进程） |

两者共用同一份 `src/` 逻辑，没有第二套实现。

### 为什么改完能立刻生效

分界线不是「脚本 vs 插件」，而是**这东西在「用的时候」会不会被重新读**：

| 改动落在 | 生效方式 | 要重启 |
|---|---|---|
| skill 正文 | 每次 `readFile` + `watchFile` 轮询 100ms | 否 |
| tool guidance / 记忆 | prompt 每次重新组装 | 否 |
| 账本 JSONL | 每次读文件 | 否 |
| 判定规则 `src/verdict.js` | `loop.mjs` 每次新进程 import | 否 |
| 插件 `lib/*.js` | Host 启动时 import 进 ESM 缓存 | **是** |

所以 RSI 自己产生的改动全部落在前四行——**它的改进不需要重启，只有改它自己的代码才需要。**

## 二、日常怎么用

### 先在界面上看

打开任意会话 → Harness 标签页 → 滚到底部 → **点「刷新」**。

你会看到：

- **Harness 改动**：账本里每条改动的文件、理由、判定
- **值得做下一个实验的信号**：哪个信号在多少个会话里可能出现（百分比）

这一块读的是三个实时端点，不是缓存。

### 再看命令行（写操作）

```powershell
cd <本库路径>\plugins\harness-eval

npm test                        # 144 项测试
npm run gate                    # 重启前必跑：能不能打开
npm run verify                  # 两个读取器是否一致 + 投影是否挂载
npm run export -- --out x.jsonl # 导出所有会话证据

npm run loop -- --status        # 当前有哪些改动在生效
npm run loop -- --probe         # 实时读数（同面板，命令行版）
npm run loop -- --candidates    # 候选靶子排序
npm run loop -- --judge <id>    # 判定某个改动，自动保留或回滚
npm run loop -- --revert <id>   # 手动回滚
```

### 最常用的一条

```powershell
npm run loop -- --judge <change-id>
```

它会：测量改动前后 → 判定 → 有效就留着、无效就回滚、证据不够就明说缺什么。

**注意 `--judge` 会改文件**（应用或回滚），所以它只在命令行，不在面板上。

## 三、四层各自在干什么

### S1 观测层

数据来源：会话日志（`sessions/*/session.v4.jsonl.zstd`，逐帧 zstd）。

记录的字段：

| 字段 | 来源事件 | 为什么重要 |
|---|---|---|
| `inputTokens` / `outputTokens` / `cacheReadTokens` | `assistant/message.usage` | 「重跑要多少钱」是 token 问题。**不要用 `totalTokens`**，真实数据里 1187/1193 条它不等于 input+output |
| `firstIncompleteTurn` | `turn/end.reason` | **只算真失败**。用户主动中断/中止不算断点（曾把 46% 的中断误判为失败） |
| `errorCodes` | `tool/result.error.code` | 区分「没先读就写」和「网络被封」 |
| `retries` | `llm/retry` | 传输抖动不是 agent 犯错，单独计 |
| `repeats` | `tool/call` 的 name+参数哈希 | 「经验没有累积」的直接信号 |
| `signature` | `request/header` + `system/message` | 没有它，两次运行根本没法比 |

### S2 对比层

判断一个「兄弟组」是否可比。四种拒绝原因：

- `neverRan` — 有子会话但一个都没跑
- `notForks` — 是 subagent 不是 fork（`cut: null` 不等于「同一个切点」）
- `differentCut` — 从不同位置分叉，起点不同
- `differentPrompt` — 收到的任务不同

**当前真实数据**：151 个会话 → 6 个兄弟组 → **0 组可比**。这个结果本身就是结论：过去没人做过受控对比。

### S3 行动层

- **账本**：`reports/harness-eval-ledger/changes.jsonl`，每条含 before-image，可读可 diff
- **边界**：只允许写 `packages/preset/agent-preset/skills/` 下面，前缀攻击（`skills-evil`）会抛 `ScopeError`
- **回滚**：文件删除 + 空目录清理，沙盒测过

### S4 判定层

规则写死在 `src/verdict.js`，不可调节（要说改就改代码）：

| 条件 | 结论 |
|---|---|
| 任一侧 < 3 个会话 | `inconclusive`（not-enough-samples） |
| 成本涨 > 5% | `reverted`（cost-rose，哪怕指标变好） |
| 指标变差 | `reverted`（metric-worsened） |
| 变化 < 20% | `inconclusive`（within-noise） |
| 指标好 ≥ 20% 且成本没涨 | `kept` |

两个刻意的设计：

1. **按会话算比率，不按总量**。否则跑得多的那一侧会被奖励。
2. **`inconclusive` 不动作**。证据不足时猜，是这套系统最该避免的事。

## 四、历史：两次失败实验的完整记录

**当前没有在生效的改动**（`npm run loop -- --status` 会显示 0 条）。

### 实验一：GUI 重复截图（靶子选错）

| 项 | 结果 |
|---|---|
| 改动 | 新增 skill `gui-observation`（`chg-1468790f`） |
| 判定 | `inconclusive (no-exposure)` |
| 原因 | after 侧 6 个会话，**GUI 调用 0 次** |
| 处置 | 已回滚（`chg-d7e66c06`），skill 目录已删除 |

**教训**：76 个会话里只有 7 个用过 GUI 工具。靶子不在日常路径上，等多久都等不到样本。

### 实验二：改文件前先读（形式选错）

第二个实验选了 `FS_NOT_OBSERVED`（73 次 / 17 会话）。这次靶子的各项指标都好：单一问题、原因明确、覆盖率 24%、还在增长。

| 项 | 结果 |
|---|---|
| 改动 | 新增 skill `edit-discipline`（`chg-1848924f`） |
| 判定 | **`reverted`**（`chg-7d325382`） |
| 原因 | **同一会话内，刚读完这个 skill，紧接着连续改文件仍然「没读就改」被拒** |
| 处置 | 已回滚（`chg-7ca234cc`） |

**这是最有价值的一次实验，因为它是负面的。** 完整过程：

1. 读完 skill（内容里明确写着「改前必读」）
2. 改 `_exp-a.txt` —— 先读了，**成功**
3. 改 `_exp-b.txt` —— **没读，被拒**
4. 中间间隔不到一分钟

数据也支持「它本来就知道」：73 次失败里有 **63 次**在失败后 3 步内立刻先去 `read` 再重试成功。

**结论见第六节**：skill 治「不知道」，治不了「知道但执行序列中途忘了」。

### 那个已被回滚的 guard 有个已知缺陷

它只比对参数，改个无关参数（比如 `max_dimension`）就能绕过。没修是因为：

> 可靠的判据需要知道「画面是否真的变了」，那要么比截图哈希、要么比窗口状态哈希，代价高且容易误判。**做一个不可靠的判断比不做更糟。**

代码还在 `src/gui-guard.js`，作为 S3 的例子保留；要重新启用需先解决这个缺陷。

## 五、换目标怎么做

想换靶子，走这三步：

1. **确认可量化**：这个问题的指标是什么？能在日志里数出来吗？
2. **确认原因已知**：知道该改什么吗？只知道现象不算。
3. **确认改动局部**：改完之后，能不能说清「只有这个场景受影响」？

还要加一条第 4 步，是这次教训换来的：

4. **确认它会真的发生**：这个指标在你日常使用里出现的频率是多少？如果一周才碰一次，攒够样本要一个月。

还有第 5 步，是 2026-10-21 挖 `uncoded` 时换来的，也是最容易忽略的一条：

5. **确认它是「一个问题」，不是「一堆问题的集合」**：一个信号有 168 次，不等于有一个 168 次的问题。拆开之后可能每个只有 2–8 个会话，而且大半是环境限制、参数用错、前置条件不满足——**没有一条能靠改代码修掉**。

**第 6 步，是最重要的一条，来自两次失败实验（见第六节）**：

6. **确认改动能落在执行路径上**：你要写的是**代码/前置检查**，还是**一份要模型主动遵守的文档**？

   如果是文档——**不要做**。两次实测都证明无效，其中一次在同一个会话里刚读完就失效。

六条都满足才值得做。举例：

| 目标 | 可量化 | 原因已知 | 改动局部 | 覆盖率 | 单一问题 | **执行路径** | 结论 |
|---|---|---|---|---|---|---|---|
| GUI 重复调用 | ✅ | ✅ | ✅ | ❌ **7/76** | ✅ | ⚠️ guard 可做 | **已放弃**（等不到样本） |
| auto-review 被上游拒绝 | ✅ | ✅ | ✅ | ✅ 42 次/9 会话 | ✅ | ✅ **改代码** | **已修并验证** |
| `FS_NOT_OBSERVED`（73 次） | ✅ | ✅ | ✅ | ✅ 17/72 | ✅ | ❌ **只能写文档** | **实验证伪**（见第六节） |
| `uncoded`（168 次，27/66 会话） | ✅ | ❌ | ❌ | ✅ 41% | ❌ **六个不同原因** | — | **已否决**（见下） |
| skill 措辞 | ⚠️ 难量化 | ✅ | ✅ | — | — | 需先定义指标 |

### `uncoded` 为什么被否决（2026-10-21 实测）

41% 的会话都有它，看着是最肥的靶子。拆开之后是六个互不相关的来源：

| 类别 | 次数 | 会话 | 根因 | 能不能改代码修 |
|---|---|---|---|---|
| CUA 会话过期 | 19 | 8 | 复用已结束的 `start_session` label | 只能改提示 |
| graph 状态机 | 18 | 4 | 前置条件不满足（错误消息已说清） | 只能改提示 |
| PTY 启动失败 | 17 | 2 | 未知 | 得先查原因 |
| ACL 权限 | 12 | 4 | `SetNamedSecurityInfoW` Win32 5 | **不是软件问题** |
| inspect 超时 | 7 | 5 | client provider 不可用 | 已知限制 |
| CUA 派发/参数 | ~16 | — | 参数用错 | 只能改提示 |

**结论：覆盖率最高的信号，往往是最不该做的靶子。** 它大是因为它把所有说不清的东西都收进来了。

正确的找靶方向因此要改：不是找「错误最多的信号」，而是找「**某类操作反复做但做得不好**」——GUI 重复调用是这种，auto-review 也是这种（一个字段让所有 review 失败）。那是行为问题，不是环境问题。

## 六、最重要的一条：改动必须落在执行路径上

**这条是 2026-10-21 用两次失败实验换来的，写在最前面，因为它否决了绝大多数候选。**

### 两次实验，同一个结局

| 实验 | 改动形式 | 结果 |
|---|---|---|
| GUI 重复截图 | 新增 `gui-observation` skill，讲「什么时候别截」 | **无效**——用户根本不走 GUI，且 skill 要主动查 |
| 改文件没先读 | 新增 `edit-discipline` skill，讲「改前必读」 | **同一会话内就失效** |

第二个实验尤其致命：**我在同一个会话里，刚读完这个 skill，紧接着连续改文件时仍然「没读就改」被拒**。

顺序是这样的：读 skill → 改 `_exp-a.txt`（我先读了，成功）→ 改 `_exp-b.txt`（**没读，被拒**）。中间隔了不到一分钟。

### 为什么 skill 治不了这个

| 失败模式 | skill 能治吗 |
|---|---|
| 模型**不知道**规则 | ✅ 能，读一次就记住 |
| 模型**知道但执行序列中途忘了** | ❌ **不能** |

真实现场是第二种。而且数据支持这一点：73 次 `FS_NOT_OBSERVED` 里，**63 次在失败后 3 步内立刻先去 read 再重试成功**。

> 它一直都知道要先读。它只是在小批量连续操作里，第二步开始就忘了。

### 所以候选设计的第一问

> **这个改动，是执行路径上必然经过的一步，还是要模型主动想起来遵守的文档？**

| 形式 | 生效方式 | 实测 |
|---|---|---|
| 改代码（auto-review 删 `temperature`） | 执行路径强制经过 | ✅ **33 次失败归零** |
| 前置检查（`tools.guard` 拦重复调用） | 执行路径强制经过 | ⚠️ 部分有效（有绕过缺陷，但确实拦住了 6 次） |
| **skill 文档** | 模型要主动查 + 主动遵守 | ❌ **两次都无效** |
| tool guidance / 记忆 | 每次进 prompt，但不强制 | ⚠️ 未验证 |

**RSI 唯一一次的完整成功（auto-review）是改代码。两次失败都是写文档。** 这不是巧合。

### 这条结论和另一个需求的冲突（未解决）

「只改执行路径」几乎都意味着改代码 = **要重启 Host**。
而另一个需求是「RSI 的变更不能靠重启才生效」。

**这两个直接矛盾。**

目前的状态是：改 skill 能热生效但无效；改代码有效但必须重启。**没有一个既热生效又有效的改动形式被验证过。**

唯一的候选是 `tools.guard` —— 它在执行路径上（算「有效」侧），但它是插件代码（算「要重启」侧）。所以 guard 类改动仍需一次重启。

**结论：要真正做成「热生效 + 有效」，需要找到一种「在执行路径上，但通过数据而非代码驱动」的机制**——比如让 guard 读一个热重载的配置文件。这条路没试过。

## 七、我踩过并修掉的坑（别再踩）

| 坑 | 症状 | 修法 |
|---|---|---|
| `ctx.systemPrompt.getSectionOrder(name)` 抛错 | 插件整个 `apply` 中止，工具**静默不注册** | 用纯数字 order |
| `inject.optional` | 服务不存在时整个插件不激活，证据页跟着消失 | 用数组 `inject` + `ctx.get` |
| 投影 state 存原始工具参数 | 单会话 470KB | 存哈希 |
| guard 拒绝无 `error.code` | 会混进 `uncoded`，把插件造成的错误算到模型头上 | 独立分类 `guard/repeated-observation` |
| guard 拦截仍记作 `tool/call` | 指标会把拦截算成重复，**会反转结论** | probe 里单独计 `guardDenials` |
| `$HOME` 在 PowerShell 是只读变量 | 赋值静默失败，查错目录 | 用普通变量名或 `$env:DSH_HOME` |
| 侧边对比用总量 | 奖励跑得多的一侧 | 按会话算比率 |

## 八、重启前检查清单

```powershell
npm test        # 必须全绿
npm run gate    # 必须 PASS
```

`gate.mjs` 会做这几件事（都不是单元测试能覆盖的）：

1. 用真实会话日志折叠 → 过 `stateSchema` → `wire.view` → `viewSchema`
2. 检查无损 JSON、无 `undefined`（这两样历史上分别导致过「界面永远空」和「新建会话回滚」）
3. 用真实 `lib/client.js` 渲染每个真实 payload
4. **在真实 Cordis Context 上挂载整个插件**，断言每个工具真的注册了
5. **断言 guard 真的拦截**：第一次放行、第二次相同调用必须拒绝
6. 检查投影 state 体积（中位数 + p95 + 最大值）

它做过变异测试：往 view 塞 `undefined`、让 fold 抛错、让渲染抛错、让 guard 失效——全部能拦下。

## 九、验证陷阱：exposure 为 0 时不要下结论

**这是这个项目最贵的教训，值得单独一节。**

一个错误从 42 次降到 0 次，可能是修好了，也可能是**它再没被触发过**。两者在数字上完全一样。

### 真实案例（2026-10-21）

`auto-review` 报「Auto review of tool ... failed; its body was not executed」33–42 次。我改了代码，重启，查日志：**0 次失败**。

我差点说「修好了」。但真相是：

| 检查 | 结果 |
|---|---|
| 重启后有没有会话跑过 review | **没有** |
| 当前权限预设 | `workspace-write`，而 auto-review 只在 `auto` 预设下运行 |
| 暴露量（exposure） | **0** |

也就是说：`auto-review` 一次都没被调用过。「0 次失败」什么都不证明。

### 怎么避免

**下结论前，先证明「它有机会发生」。**

问三个问题：

1. 这个错误发生需要什么前置条件？（这里是：预设=auto + approval=ask + 有工具调用）
2. 我的样本里，这些条件满足了几次？
3. 如果一次都没有，那我的「修复成功」是编出来的。

### 检验自己有没有踩坑的一句话

> 「如果我把修复完全撤销，我的数据会变吗？」

- 会变 → 有 exposure，结论有效
- 不会变 → **没 exposure，结论无效**

### 代码里的对应实现

`src/verdict.js` 的 `no-exposure` 检查就是这件事的固化：

```js
if (after.exposure !== undefined && after.exposure === 0) {
  return { verdict: 'inconclusive', reason: 'no-exposure', ... }
}
```

`probe.mjs` 提供 `exposure = sessionsWithGui`（能产生该指标的会话数）。换成别的靶子时，这个字段要换成对应的「前置条件满足数」。

### 更早的一次同类踩坑

同一个错误我犯了三次：

1. **GUI 重复调用**：判定给出 `kept`（重复降 100%），实际是 after 侧 6 个会话**零次 GUI 调用**
2. **再次判定**：仍是 `inconclusive (no-exposure)`，但我一度读成「还在等样本」
3. **auto-review**：`0 次失败`，实际是预设没切到 auto

三次都是同一个形状：**指标为 0 被误读成变好了**。

### 反面：把历史数据当成当前问题（第四次）

修好 auto-review 之后，我数了一次全库的失败次数：**33 次**。差点当场推翻自己的修复。

真相是 33 次全部发生在修复提交之前，之后是 0。我忘了按时间切分。

**规则：任何计数都必须带时间窗。** 全库累计的数字回答不了「现在还好吗」，只能回答「历史上发生过多少」——那已经不是同一个问题。

```js
// 错：在全部历史里找这个错误
for (const event of allEvents) if (isAutoReviewError(event)) count++

// 对：只在改动之后找
for (const event of allEvents) if (event.at > fixCommitTime && isAutoReviewError(event)) count++
```

这一条和 exposure 是同一个陷阱的两面：

| 陷阱 | 表现 | 后果 |
|---|---|---|
| **没有 exposure** | 指标为 0，但没有机会发生 | 把「没跑过」当成「好了」 |
| **没有时间窗** | 计数包含历史 | 把「已经修好」当成「还在坏」 |

一个让你过早乐观，一个让你错误回滚。两个都要防。

## 十、界面：改动面板与实时读数

### 三个只读端点

标签页原来读投影缓存，只有会话提交事件时才前进，所以显示的是几分钟前的数字。这三个 GET 端点改为按需读日志：

| 端点 | 返回 |
|---|---|
| `GET /api/harness-eval/status` | 在生效的改动，含判定 |
| `GET /api/harness-eval/probe` | 实时读数：会话数、指标、成本、exposure |
| `GET /api/harness-eval/candidates` | 候选信号按覆盖率排序 |

都不需要 token（`policy: 'open'`），因为只读且不含敏感内容。

### 标签页底部的「Harness 改动」面板

点「刷新」→ 拉上面两个端点：

- 账本里的每条改动：改了哪个文件、为什么改、判定是什么
- 候选靶子：哪个信号在多少个会话里可能出现（百分比）

**没有「回滚」按钮**，只有命令提示 `npm run loop -- --revert <id>`。这是刻意的：给按钮等于暗示循环有权自己决定去留。

### 为什么写操作不做成 HTTP

`judge` 会**应用或回滚一个文件**。暴露成 HTTP，任何能访问这个端口的东西都能改你的 skill。那需要 token 和鉴权，不是一个便利开关。而且：

- 写路径是改得最频繁的部分。留在脚本里，改它不用重启
- 路由处理器只加载一次进 ESM 缓存，改它要重启

**这是"看"和"改"分开的实质原因，不只是设计偏好。**

### 实施中踩的坑

| 坑 | 后果 | 修法 |
|---|---|---|
| `webServer.register` 不是函数时直接抛错 | 整个 `apply` 中断，证据页消失 | 检查方法而非只检查服务存在 |
| `webServer` 可能在 `apply` 之后才激活 | 路由静默不注册 | 轮询重试（学 `dsh-graph`），失败要报告 |
| 门禁没断言路由注册 | 路由没挂上也 PASS | 补 3 条断言 + 变异测试 |

## 十一、下一步能做什么

按价值排序：

1. **解决「热生效 × 有效」的矛盾**（见第六节）：目前只有「改代码」被证明有效，但它必须重启。唯一有希望的中间态是**让 guard 读一个热重载的配置文件**——guard 在执行路径上（有效），配置热读（不重启）。这条路没试过，是最值得做的下一步。
2. **不再写 skill 类候选**：两次实测都无效，见第六节。这不是偏好问题，是结论。
3. **不再按「错误最多」选靶**：`uncoded` 被否决（见第五节），方向改为找「某类操作反复做但做得不好」。
4. **修 guard 判据** → 需要「上次动作是否真改变画面」，是硬问题（已回滚，等有可靠判据再做）。
5. **自动生成候选** → 目前这一步是人工的，代码化需要判断「这个重复该用什么规则修」。
6. **auto-review 修复合给上游** → 一行改动、证据完整，合了以后少一处同步冲突点。

### 一个已验证可行的中间态（未实现）

`tools.guard` 是同步函数（`(execution) => string | undefined`），**可以同步读文件**（`readFileSync` 可用，已验证）。这意味着：

```
guard 每次被调用 → readFileSync 一个 JSON 策略文件 → 按策略判断
```

改策略 = 改那个 JSON = **热生效**；判断逻辑在 guard 里 = **执行路径上必然经过**。

这可能是唯一能同时满足两个需求的形状。代价是每次工具调用都做一次同步文件读（可加 mtime 缓存）。

## 十二、成功案例：auto-review 被上游拒绝（供参照）

这是目前为止**唯一一个走完整闭环并验证成功**的改动。把它记下来，因为下次做别的靶子时可以对照。

### 现象

工具调用被判失败，报：

```
Auto review of tool "write" failed; its body was not executed:
auto-review: reviewer ended with error INVALID_REQUEST: 400:
{"message":"workbuddy 上游失败：请求被上游拒绝（http 400）（code 11133）…"}
```

**关键**：`its body was not executed` —— 工具**没被执行**。agent 想做一件事，被一个它看不见的复核环节挡掉了。

### 排查路径

| 步骤 | 发现 |
|---|---|
| 数次数 | 33–42 次，分布在 5–9 个会话 |
| 抽错误码 | `INVALID_REQUEST` 28 次，`SERVER` 9 次，`RATE_LIMIT` 2 次 |
| 分 provider | 29 次集中在 workbuddy |
| **排除长度** | 1.8 万字符的小会话也失败 → 不是内容太长 |
| **排除账号** | 错误消息自述「池中其余账号本次请求都已尝试过」 |
| **找代码差异** | 全仓库搜 `temperature` → **只有 auto-review 传了 `temperature: 0`** |
| 读错误原文 | `the request parameters were rejected` —— 是 **parameters**，不是 content |

### 修复

`src/index.ts` 删掉 `temperature: 0`，测试断言改为「不得有 temperature」。

### 验证（关键：证明 exposure > 0）

之前三轮我都没验证成，因为**预设没切到 auto**（auto-review 只在 `auto` 预设下运行，源码 L690/L730）。

真正验证成功的条件是三个同时成立：

```
preset = auto        （日志 seq 4277）
approval = ask       （日志 seq 4278）
之后有真实工具调用     （seq 4315 的 write）
```

结果：**auto-review 错误 0 次**。对比历史上相同条件的会话报 5–10 次。

### 为什么这次修对了

- 原因已知（参数被拒，不是内容问题）
- 改动局部（一个字段）
- **覆盖率足够**（42 次/9 会话，天天会遇到）

这三条正好是 GUI 那个靶子缺的第三条。

### 留下的模式

| 阶段 | 具体做法 |
|---|---|
| 找靶子 | 先按 errors 分组数次数，按覆盖率排序，不看「哪个最有意思」 |
| 定假设 | 找代码差异（全仓库搜索 + 定位唯一不同点） |
| 排除干扰 | 逐条排除：长度、账号、网络、内容 |
| 验证前 | **先确认 exposure**：前置条件满足几次 |
| 验证后 | 对比同条件下的历史数据，而不是绝对数字 |
